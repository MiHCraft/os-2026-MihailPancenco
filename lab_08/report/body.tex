The child prints its own PID, builds a NUL-terminated array of strings, and calls \texttt{exec("echo",\allowbreak{} args)}. The parent calls \texttt{wait(\&status)} and reports the child's status. The Makefile includes \texttt{run} in \texttt{UPROGS}.

The lifecycle is the same: fork creates a separate process with inherited descriptors and memory contents; exec replaces the child image while retaining its PID; wait synchronizes with termination and reaps it. Linux \texttt{execlp} is a libc helper with PATH search and a variadic argument list. xv6's \texttt{exec} takes an explicit pathname and argument vector and does no PATH search. xv6 \texttt{wait} waits for a child and stores the exit value directly; Linux waitpid can select a child and returns an encoded status decoded with wait macros.

\subsection{2. Who prints hello from the child}

The \texttt{echo} program prints it. Before exec, \texttt{run} prints only the parent and child PID messages. Successful exec never returns to the old program; the new echo image uses the supplied argument strings to produce \texttt{hello from the child}.

\subsection{3. Why the failure statuses differ}

The xv6 branch after failed exec explicitly calls \texttt{exit(1)}, so its parent prints status 1. The Linux branch explicitly calls \texttt{exit(127)}, so its parent prints 127 after decoding it. The values were chosen by the programs; exec itself returns an error to the caller instead of automatically deciding this exit status. The xv6 parent still exits 0 after reporting its child, as in the supplied example.

\section{Part 2 - pingpong}

\texttt{user/\allowbreak{}pingpong.c} creates two pipes, \texttt{p2c} and \texttt{c2p}. The child closes \texttt{p2c[1]} and \texttt{c2p[0]}; the parent closes \texttt{p2c[0]} and \texttt{c2p[1]}. The parent initializes the byte to \texttt{p}, writes it to the first pipe, and waits in a read on the second pipe. The child reads the byte, prints its ping message, writes the byte back, closes its descriptors and exits. The parent receives the reply, prints pong, closes descriptors and reaps the child.

\begin{lstlisting}[style=terminal]
parent p2c[1] -- one byte --> p2c[0] child
parent c2p[0] <-- one byte -- c2p[1] child
\end{lstlisting}

\begin{lstlisting}[style=terminal]
$ pingpong
64: received ping
63: received pong
\end{lstlisting}

The actual child PID is 64 and the parent PID is 63. The order is guaranteed by the code: the child prints ping before writing the reply, and the parent prints pong only after receiving it. Scheduler timing may delay either process, but cannot reverse these messages in a successful exchange. Pipe, fork, read, write and wait errors are checked; a failed exchange exits nonzero.

\subsection{1. Why two pipes}

A pipe is a one-way byte stream. Using a separate pipe per direction gives each process an unambiguous input and output channel. If both processes read and write a single shared pipe, either can consume its own byte because a pipe does not address messages to particular readers. Two pipes implement the required reliable round trip without that race.

\subsection{2. Which call waits for the reply}

The parent's \texttt{read(c2p[0],\allowbreak{} \&b,\allowbreak{} 1)} blocks while there are no bytes available and a writer remains open. The child writing its reply makes that read complete. The later \texttt{wait(\&status)} reaps the child; it is not what makes the parent wait for the reply byte. Closing unused write ends also ensures a failed/exited peer can produce EOF rather than leaving a reader blocked indefinitely.

\section{Optional - Prime sieve}

\texttt{user/\allowbreak{}primes.c} generates integers 2 through 35 and builds a process chain. Each filter reads its first integer as a prime, prints it, and forwards only integers not divisible by that prime through a new pipe to its child. Reads and writes transfer one integer at a time. Every process closes inherited unused ends and its output end when input reaches EOF, then waits for its child. The empty final stage exits without printing.

\begin{lstlisting}[style=terminal]
$ primes
prime 2
prime 3
prime 5
prime 7
prime 11
prime 13
prime 17
prime 19
prime 23
prime 29
prime 31
\end{lstlisting}

The output matches all eleven primes in the inclusive interval 2 through 35. Closing the final writers propagates EOF through the chain so all filters can exit. Keeping only necessary descriptors also stays within xv6's per-process descriptor limit.
