\section{Environment}

The programs were compiled and executed inside Ubuntu 26.04.1 LTS (ARM64) in VirtualBox as non-root user \texttt{misa} on 23 October 2026. The working directory was \texttt{\textasciitilde{}/\allowbreak{}os-labs-04-08-20261023/\allowbreak{}lab07}. GCC 15.2.0 compiled all seven programs with C11, \texttt{-Wall -Wextra -Werror -O2}. Screenshots and \texttt{terminal-output.txt} record the actual runs.

\section{Part 1 - fork, exec and wait}

\texttt{run.c} follows the supplied program: the parent prints and flushes its PID, forks, and waits for its child; the child prints its own PID and parent PID and uses execlp to become ls -l. Flushing before fork prevents buffered parent text from being duplicated when output is redirected. The date and nonexistent-program changes are kept as separate sources \texttt{run\_date.c} and \texttt{run\_missing.c} so each required case remains runnable.

\subsection{1. Why perror runs only for nosuchprog}

Successful execlp replaces the child's process image and does not return to the following line. The same PID now runs ls or date. On failure it returns -1 and sets errno, so \texttt{perror("exec")} executes and prints \texttt{No such file or directory}. The supplied failure branch then calls \texttt{exit(127)}.

\subsection{2. Whose PID appears as my parent?}

In the recorded run, the parent PID was \textbf{37341}, the child PID was \textbf{37342}, and the child printed \textbf{37341} as its parent. getpid returns the caller's own PID; getppid returns its current parent's PID. The parent stays alive and waits during this test.

\subsection{3. Statuses for ls and nosuchprog}

The parent reported child status \textbf{0} for ls/date and \textbf{127} for the nonexistent program. Linux waitpid returns an encoded wait status, so WEXITSTATUS extracts the normal exit value. The supplied parent itself returns 0 after printing the child's result, including the failure experiment. A general-purpose shell would additionally check normal versus signal termination before interpreting the status.

\section{Part 2 - A zombie, on purpose}

\texttt{zombie.c} is the ls version with \texttt{sleep(20)} immediately before waitpid. It was started in the background; after two seconds the process table showed the parent sleeping and the exited child unreaped.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.74\textheight,keepaspectratio]{img/07_03_zombie.png}
\caption{The exited ls child is visible with state Z while its parent sleeps.}
\end{figure}

\subsection{1. The STAT letter and its meaning}

The ls child PID \textbf{37876} had state \textbf{Z}, and its command appeared as \texttt{[ls] <defunct>}. A zombie has finished executing, but the kernel retains its exit information and process-table identity until the parent consumes them. Parent PID \textbf{37875} had state S because it was sleeping.

\subsection{2. What makes the zombie disappear}

After the sleep ended, \texttt{waitpid(pid,\allowbreak{} \&status,\allowbreak{} 0)} reaped the child. A later ps query for 37876 printed only the header, with no process row. Waiting for time to pass does not itself remove a zombie; the parent's wait call does.

\section{Part 3 - Redirection}

The child in \texttt{redirect.c} closes descriptor 1, opens out.txt with \texttt{O\_WRONLY | O\_CREAT | O\_TRUNC} and mode 0644, then executes ls -l. The parent waits and prints its completion message. The implementation checks fork/open/exec/wait errors.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.74\textheight,keepaspectratio]{img/07_05_redirection.png}
\caption{Descriptor 1 is reused by open and the unchanged ls listing appears in out.txt.}
\end{figure}

\subsection{1. Which descriptor open returned, and why}

The diagnostic reported \textbf{1}. Standard descriptors 0, 1 and 2 were initially open; closing 1 made it the lowest available slot. open chooses that lowest free descriptor. The mode 0644 requested for out.txt already excludes group write, so umask 0002 does not add it back.

\subsection{2. Why ls no longer prints its listing to the screen}

ls still writes to descriptor 1. The child changed what that descriptor refers to before exec; the descriptor remains open across exec and is inherited by the new image. It now points to out.txt. The diagnostic is written to stderr (2), and the parent's own stdout remains unchanged, so both remain visible.

\subsection{3. Redirecting errors instead}

For \texttt{2> err.txt}, close descriptor \textbf{2} before opening the destination, while leaving 0 and 1 open. A more general implementation can use dup2 to choose descriptor 2 explicitly. Descriptor 1 is stdout and descriptor 2 is stderr.

\section{Part 4 - A pipe}

\texttt{pipeline.c} creates a pipe and two children. In the producer, close plus dup connects descriptor 1 to the pipe's write end before exec of ls /etc. In the consumer it connects descriptor 0 to the read end before exec of wc -l. Each child closes the original pipe descriptors after duplication; the parent closes both ends and waits for both children.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.74\textheight,keepaspectratio]{img/07_06_pipelines.png}
\caption{Both the two-stage and three-stage programs match their Ubuntu shell pipelines.}
\end{figure}

\subsection{1. Compare with the real shell}

Both returned \textbf{237}. The important property is equality for the same directory at the same time. ls uses one filename per line when writing into a pipe, and wc -l counts those lines.

\subsection{2. Which child stays alive after leaving the writer open}

Only a temporary copy, \texttt{pipeline\_broken.c}, omitted the parent's final close of the write end. The submitted pipeline.c remains the correct version. In the process table, broken parent PID \textbf{44821} and child \textbf{44823}, running \texttt{wc -l}, were still sleeping; ls had already exited.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.74\textheight,keepaspectratio]{img/07_07_pipe_eof.png}
\caption{Leaving the parent writer open keeps wc waiting; the temporary process group is then stopped.}
\end{figure}

\subsection{3. What wc is waiting for}

wc is waiting for EOF. After buffered bytes have been consumed, a pipe read returns EOF only when every descriptor referring to its write end is closed. The parent's unused open writer prevents EOF while the parent waits for wc. The temporary background process group was terminated after this observation, and no hanging experiment was left running.

\section{Optional - Three stages}

\texttt{pipeline3.c} implements \texttt{ls /\allowbreak{}usr/\allowbreak{}bin | grep x | wc -l} with two pipes and three children. The middle child redirects both stdin and stdout; all children and the parent close all four original pipe ends after the needed duplicates. The parent waits for every child and reports failure if any stage fails.

Both returned \textbf{231} in this Ubuntu installation. The three-stage comparison is shown alongside the two-stage result above.
