\subsection{1. Features common to both shells and features added by Bash}

Both support running executables, input/output redirection, pipes, semicolon-separated lists, background commands and parenthesized grouping. Bash additionally provides wildcard and variable expansion, quote processing, PATH search, richer built-ins, command history, completion and job management.

The xv6 LIST case explicitly forks the left command, calls \texttt{wait(0)}, and then runs the right command. Therefore \texttt{echo hello > f ; cat < f} is ordered and reads the newly written file; it is not a race between the two commands.

\subsection{2. Why ls fails after cd, and how to run it}

A standalone \texttt{cd d} changes the parent shell's working directory. xv6 does not search PATH; bare \texttt{ls} is interpreted as an executable relative to the current directory, while the program is stored in \texttt{/\allowbreak{}}. Use \texttt{/\allowbreak{}ls} or \texttt{../\allowbreak{}ls} from \texttt{d}.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.74\textheight,keepaspectratio]{img/04_04_paths.png}
\caption{Bare ls fails inside d, while absolute and parent-relative executable paths work.}
\end{figure}

In \texttt{mkdir d ; cd d ; ls ..}, the special parent-shell check does not see \texttt{cd} at the start of the line. The list parser treats it as a separate executable, which does not exist, producing \texttt{exec cd failed}. Even a real external cd could change only its own working directory, not that of the parent shell.

\subsection{3. Which missing feature I would add}

Executable search would matter most in daily use because changing directory otherwise breaks short program names. A simple fallback that tries \texttt{/\allowbreak{}command} after a failed relative exec would be the easiest useful first extension. Full Bash-compatible expansion and quoting require more parsing and expansion logic.

\subsection{1. Outputs for args *.c "x y"}

Both have argc 4, including argv[0]. Bash passes three user arguments: \texttt{a.c}, \texttt{b.c}, and the single string \texttt{x y}. xv6 passes the literal \texttt{*.c} and the two strings \texttt{"x} and \texttt{y"}. Equal counts are coincidental: changing the number of matching C files changes Bash's argc.

\subsection{2. Who expands the wildcard and removes quotes?}

The shell performs both transformations before exec. The kernel accepts an executable pathname and an already constructed argument vector; the argument-printing program only displays what it receives. Bash also replaces \texttt{\$HOME} with \texttt{/\allowbreak{}home/\allowbreak{}misa} and turns \texttt{'single quoted'} into one argument without the quote characters. xv6 passes \texttt{\$HOME} literally and splits the quoted phrase into two strings retaining the quote characters.

\subsection{3. What happened to repeated spaces?}

For \texttt{args one   two  three}, both systems report argc 4 and arguments \texttt{one}, \texttt{two}, \texttt{three}. Runs of unquoted whitespace separate words and do not create empty arguments. Bash can preserve spaces using quotes; the xv6 tokenizer does not implement that quoting rule.

\subsection{2. Where cd is handled and why}

In \texttt{main}, line 166 checks for a line beginning with \texttt{cd } and line 169 calls \texttt{chdir(cmd + 3)} before the shell forks a command. The shell itself must make the call because the current working directory is a per-process property.

\subsection{3. Why there is no wildcard or variable expansion}

Literal searches for \texttt{*} and \texttt{\$} were run on \texttt{user/\allowbreak{}sh.c}. Asterisks occur in pointer declarations and dereferences; \texttt{\$} occurs in the prompt. No expansion routine resolves filenames or environment variables. The tokenizer splits words using whitespace and syntax symbols such as \texttt{<}, \texttt{>}, \texttt{|}, \texttt{\&}, \texttt{;} and parentheses. This explains the literal asterisk, variable name and quote characters observed above.
